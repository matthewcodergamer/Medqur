# Medqur V0.2 functional architecture

V0.2 moves the product from a visual demo toward a functional clinical-workflow shell while preserving a hard boundary between prototype behaviour and production healthcare integrations.

## Functional in V0.2

- Live camera scanning on Android, iOS and supported browsers through `mobile_scanner`.
- QR plus common linear/2D barcode capture for staff badges, patient wristbands and medication packages.
- Real native device biometric prompts on Android/iOS using `local_auth`.
- Real scannable encounter and staff QR tokens.
- Local prototype persistence through `shared_preferences` so demo encounters/orders survive refreshes/restarts.
- Role policy boundary for doctor ordering/assignment and nurse medication administration.
- Patient assignment to a clinician.
- Closed-loop medication prototype: scan patient wristband, then scan the mapped medication package before administration can be recorded.
- FHIR-shaped Patient, Encounter and MedicationRequest adapter maps.
- Shared in-process patient state so doctor/nurse views update from one state model.

## Deliberately not faked

### Browser passkeys

A browser can support WebAuthn/passkeys, often unlocked by Face ID/fingerprint, but secure authentication requires a relying-party backend to issue and validate challenges. The public GitHub Pages build therefore labels browser access as prototype access instead of pretending a biometric check happened.

### NIDS / NIRA

Scanning a NIDS/NIC credential is only capture in this prototype. Authoritative identity verification, consent and minimum-data responses require the real approved NIRA interface.

### e-Care / SystmOne

No production EHR is connected. `FhirAdapter` defines the integration boundary only. Production mappings must follow the Ministry/vendor implementation guides and profiles.

### Cross-device live synchronization

`ClinicalSyncGateway` is the backend boundary. The default implementation is intentionally disconnected. A production implementation needs authenticated encrypted transport, server-side authorization, audit, conflict handling and an approved clinical datastore before nurse and doctor devices may exchange real records.

## Production backend target

A future service layer should expose authenticated APIs for:

1. OIDC/passkey staff sessions and facility/role claims.
2. Patient/encounter persistence in an approved database.
3. Realtime event delivery for queue, order and medication-task updates.
4. FHIR/HL7 integration with authoritative EHR services.
5. NIRA identity verification through approved interfaces.
6. Append-only audit events for every read/write/scan/sign action.
7. A medication/product master keyed by GTIN/GS1 identifiers and hospital unit-dose labels.

The client should never treat an arbitrary scanned barcode as proof of a drug identity. It must resolve that code against the approved medication/product master and the active signed order.
